# Building sliverreshine

Three stages: build the patched server, bake it into the launcher, build the
frontend into the launcher. Only the third one runs on every UI change.

```
build/
  build-server.ps1    BishopFox/sliver -> sliver-server binaries
  embed-payload.ps1   sliver-server -> internal/embed/serverbin/payload.gz
  build-release.ps1   assemble dist/sliverreshine-linux-amd64.zip
```

## Prerequisites

- Go 1.25+ (the launcher module declares `go 1.25.6`).
- Node 20+ for the frontend.
- A `BishopFox/sliver` checkout at **v1.7.3**, because
  `sliver_ui/backend/go.mod` pins that release and the generated protobuf
  packages must match the server's wire types.
- PowerShell 7.

## 1. Fetch the embedded compiler assets (once per checkout)

Sliver embeds a Go compiler, Zig and garble inside the server binary. Those
archives are **not** in git; the embed directive fails without them.

```powershell
cd <sliver-checkout>
go run -mod=vendor ./util/cmd/assets
```

This downloads roughly 0.6 GB into `server/assets/fs/`. One mirror is
occasionally flaky and the fetcher retries automatically — let it finish.

## 2. Build the server

```powershell
./build/build-server.ps1 -SliverDir ..\..\_refs\sliver-173 `
    -Targets linux/amd64,linux/arm64,windows/amd64 `
    -Out ..\..\_out
```

Outputs `sliver-server-<os>-<arch>` into `_out/`, ~297 MB each.

**The `server` build tag is mandatory.** `server/assets/assets_<os>_<arch>.go`
is gated behind it, and without the tag the package fails to compile with
`undefined: assetsFs`. Sliver's own Makefile uses `-tags 'go_sqlite server'`;
so does the script.

`CGO_ENABLED=0` keeps the binaries static, so the launcher needs no libc from
the host.

### Applying the source patches

Two files in the server tree are patched, and the launcher carries a third fix.

| File | Change |
|---|---|
| `server/gogo/go.go` | Pass `GOTMPDIR`/`TMPDIR`/`TMP`/`TEMP` to the `go` and `garble` subprocesses, plus a `getBuildTempDir()` helper. |
| `server/gogo/goname/rename_import.go` | Clear a stale rename destination instead of returning `target exists`. |
| `internal/launch/server.go` | `ensureExecutable` restores the execute bits on the unpacked toolchain at every launch. |

See the *Server patches* section of the top-level `README.md` for why.

## 3. Build the frontend

```powershell
cd frontend
npm ci
npm run build
```

`npm run build` runs `tsc && vite build` into `frontend/dist/`. Type errors fail
the build, so this doubles as the type check.

`npm test` additionally enforces a route contract: every path `api.ts` calls
must exist in the backend route table. The fixture lives at
`frontend/src/lib/__fixtures__/routes.json` and is regenerated by
`TestRouteTableFixture` in `internal/ui/api` — if the test fails, run it once to
rewrite the fixture and again to confirm. Adding an endpoint therefore means
touching the backend table and letting the Go test refresh the fixture.

## 4. Collect the frontend into the launcher

The launcher serves `web/dist` through `//go:embed all:dist`, so the built
assets are copied there:

```powershell
Remove-Item -Recurse -Force ..\web\dist\*
Copy-Item -Recurse -Force .\dist\* ..\web\dist\
```

## 5. Bake in the server

```powershell
./build/embed-payload.ps1 -Server ..\..\_out\sliver-server-linux-amd64
```

Writes `internal/embed/serverbin/payload.gz` (about 95 MB for the Linux
binary). It compresses to a temp file and moves it into place, so an
interrupted run never leaves a truncated payload embedded.

## 6. Build the launcher

```powershell
# release build: server is embedded
$env:GOOS='linux'; $env:GOARCH='amd64'; $env:CGO_ENABLED='0'
go build -tags embedserver -trimpath -o dist/sliverreshine ./cmd/sliverreshine
```

Without the `embedserver` tag the launcher builds against
`internal/embed/embed_dev.go`, where `Payload` is nil. It then looks for a
`sliver-server` binary next to the executable or on `PATH` — that is the fast
loop for backend work, because it skips the 95 MB embed and a full relink.

## 7. Package

```powershell
./build/build-release.ps1 -Server ..\..\_out\sliver-server-linux-amd64
```

Produces `dist/sliverreshine-linux-amd64.zip` containing `sliverreshine`, `run.sh` and
`README.md`. The server is *inside* the binary, so the archive stays around
100 MB.

## Fast iteration

Backend/API work:

```powershell
go build ./... && go test ./...
```

UI work — leave `npm run dev` running in `frontend/`; Vite proxies `/api` to the
console. Rebuild the launcher only when Go code changes.

## Verifying a build

The checklist that matters after any change to the server patches:
1. Extract the zip on a clean machine or container.
2. `./run.sh` — expect `compiler assets ready`, `sliver server ready`, and
   `web console listening on http://0.0.0.0:8080`.
3. Confirm the console header shows `CONNECTED` and the version, and that
   `/api/rpc/methods` reports **183** methods. That count is the coverage check:
   it is the size of the generated `SliverRPC` surface, and the raw RPC page is
   what makes every one of them reachable.
4. **Build the same implant name twice.** The second build is the regression test
   for patches 1 and 2 — a repeat build exercises both the compiler temp dir and
   the staging-tree rename.
5. Download the artifact and check the magic: `MZ` for Windows, `\x7fELF` for
   Linux.
6. On Linux only, confirm the execute bits survived unpacking — this is the
   regression test for patch 3:

   ```bash
   stat -c '%A %n' home/sliver/go/bin/go home/sliver/go/pkg/tool/linux_amd64/compile
   # both must start with -rwx
   ```

7. Run an implant on the target and drive it from the console: `exec`, a
   filesystem listing, and a process listing. The session must report
8. Run an implant on the target and drive it from the console: `exec`, a
   filesystem listing, and a process listing. The session must report
   `interactive=True` for the terminal tab to work.

## Locale files are UTF-8 — never use `Set-Content` on them

`Set-Content` / `Out-File` without an explicit `-Encoding` write the ANSI code
page. On a system whose ANSI page is not UTF-8, running either over a source
file **destroys characters permanently**: every byte with no mapping becomes
`?`, and the code page's two-byte pairing can swallow the character after it
(`'Connecting…',` becomes `'Connecting?,` — the closing quote is gone). The
result is not a misrendering that a re-decode can undo; the information is no
longer in the file.

Use the `write`/`edit` tools, or an explicit `-Encoding utf8`, for any file
containing non-ASCII. `frontend/src/i18n/locales/*.ts` and the Chinese strings
in `internal/ui/sliver/persistence.go` are the ones that matter here.

Guards, all run from `frontend/` unless noted:

```powershell
python ..\build\sweep_encoding.py ..       # any file that is not valid UTF-8
python scripts\check_keys_exist.py         # every t('...') key exists in en+zh
python scripts\check_unused_i18n.py        # declared-but-unused / used-but-undeclared
```

If damage does happen, `build/rebuild_locales.py` regenerates both locale files
from the last good Vite bundle. See the recovery section below.

## Recovering damaged locale files

A Vite bundle is the recovery source, because it carries the locale objects as
plain string literals and is written by a tool that always emits UTF-8. Any
bundle built before the damage will do; the newest one is best.

```powershell
# 1. Pull the en/zh locale objects out of the bundle into JSON.
python build\recover_locales.py frontend\dist\assets\index-*.js build

# 2. Regenerate both .ts files from those JSON objects, layering the
#    refactors that landed after the bundle was built back on top.
python build\rebuild_locales.py

# 3. Confirm the result.
python build\sweep_encoding.py .
python build\verify_delta.py
cd frontend; python scripts\check_keys_exist.py
```

Two things to know about step 2:

- **`DROP` and `NEW_KEYS` in `rebuild_locales.py` are the delta** between the
  bundle and the current source. If the bundle predates a refactor that moved
  keys between sections, that move has to be described there or the rebuild will
  either resurrect dead keys or lose live ones. Both languages are built from
  one key list, so en/zh parity holds by construction.
- **Step 1 needs a bundle that still exists.** `frontend/dist/` is build output
  and gets overwritten by the next `vite build`, which is why the recovered JSON
  is worth keeping once produced. The corrupted originals are kept under
  `build/damaged-backup/` for reference only — they are not recoverable.
